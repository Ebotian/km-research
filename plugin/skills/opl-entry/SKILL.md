# open-problem-lab 总纲

本插件是一套本地工具链。**命令不在工作区里**——agent 的 cwd 是用户工作区，而命令在
插件目录的 `bin/` 下，所以写 `bin/opl-…` 会 `No such file or directory`。先定位一次：

```bash
# 下文用 $OPL 指代插件的 bin 目录
OPL="${KIMI_PLUGIN_ROOT:-<插件根>}/bin"
```

所有命令共用一套接口约定，先记住它——**判决走退出码，不走文本**。

**但退出码只回答「这个命令做完了吗」，不回答「结论成立吗」。** 这两件事必须分开看：
`opl-search` 在 unsat 时返回 `0`，意思是「我找到了一份证明」，**不是**「这份证明已被
独立复核」——复核是 `opl-certcheck` 的事，而它可能报 `3`（无法判定）。同理
`opl-leancheck` 返回 `0` 只说明内核接受了这份文件。研究结论落在**结构化字段**上：
台账的 `formal_status` / `verification_level`、证据记录的 `verdict`。

| 码 | 判决 | 含义 |
|---|---|---|
| `0` | `PASS` | **这个命令**完成了它那一步，没有出错 |
| `1` | `REJECT` | **这个命令**要证的事被推翻：找到见证、证书无效、候选不可行 |
| `2` | `USAGE` | 参数、规格或输入有错 |
| `3` | `UNKNOWN` | 无法判定，**必须**附原因 |
| `4` | `MISSING` | 所需后端不存在。**签名器也算**：找不到 `ssh-keygen` 就不写台账、也不产出无签名的证据。此时*不许*回退到估算 |
| `5` | `EMPTY` | 正常运行，但没有任何结果 |

`stdout` 只有机器可解析的内容（一行 `s <判决>` 或一个 JSON 对象）；诊断在 `stderr`。
所以管道里不会混进噪声，而且 `UNKNOWN`(3) 与「被推翻」(1) 在数值上就无法混淆。

## 三条不可协商的纪律

1. **`unknown` 绝不折叠成「已证」或「无反例」。** 超时是 `3`，不是 `1`。把「没跑出来」
   说成「不存在」，是本插件要防的头号错误。
2. **结论必须经与生成路径不同的代码复核。** 求解器说 `sat` 只说明它如此认为；
   见证要被**规格的直接求值**复核过才算数——那条路径与任何编码器无关。
3. **缺失验证器时硬失败。** 不要因为工具不可用就改用估算或心算；那正是
   `--evidence` 强制存在的原因。

| 任务 | 技能 |
|---|---|
| 为一个猜想寻找反例、排除有限域、复核疑似反例、把结果落进台账 | `opl-refute` |

## 命令速查

| 命令 | 一个职责 |
|---|---|
| `opl-capabilities` | 探测后端，产出 `capabilities.json`。含 Python 模块探测与解释器分裂检测 |
| `opl-conj` | 猜想台账。一题一文件；**状态变更必须带 `--evidence`**，否则拒绝写入。依据随记录一起存，改完的整条记录不自洽（结论、档位与依据对不上）就整笔拒绝（`2`），一个字段都不写 |
| `opl-encode` | 规格 → CNF / CP-SAT；双后端一致性检查；见证直接求值 |
| `opl-search` | 跑搜索，产出见证或 DRAT 证明 |
| `opl-certcheck` | 用独立校验器复核证书（drat-trim / lrat-check / cake_lpr / carcara） |
| `opl-leancheck` | 编译 Lean 文件并审计证明状态（公理白名单 + sorry 检测） |
| `opl-sign` | 本机签名密钥与验签。台账与证据都要求签名——**哈希是自证的**：写文件的人同时写了被引用的文件，所以一份手写的自洽假证据本来可以全盘通过 |

（都在 `$OPL` 下——即插件的 `bin/`。调用时写 `$OPL/opl-…`。）

## 动手之前先探测一次

```bash
$OPL/opl-capabilities --out lab/capabilities.json
```

它会告诉你哪些后端可用、哪些**存在但坏了**（`decompress` 就是一处已知的上游 bug）、
以及 Python 依赖是否分裂（`split_brain`）。**不要假设某个求解器可用**——缺失时要
如实报 `MISSING` 并说明，而不是换一条会给出不同结论的路。

**写台账之前先跑一次 `opl-sign init`**：它生成一份无口令的本机工具密钥，此后写出的东西
都带签名——**证据**旁挂一份 `<path>.sig`（验证器命令一次写出，没有「更新证据」这种
事务），**记录**把签名**内嵌**在文件里（顶层 `signature` 字段，于是「写入 + 签名」是
一次原子提交：签不成，盘上那条旧记录一个字节都不会动）。签名回答的是「这句话是谁
说的」，而台账原先那两层检查（记录自洽、证据的哈希与它引用的文件对得上）都挡不住
一份手写的自洽假证据：写文件的人同时写了被引用的文件。没有签名器就写台账，会以
`4 MISSING` 拒绝（缺验证器时硬失败，与「找不到 `bwrap` 就不降级到裸跑」同一条纪律）。
密钥在本机，沙箱只挂显式列出的文件，所以沙箱里的候选与评估器看不到它；但同一用户下
有 shell 的进程仍能读它——它降的是自欺的概率，不是让证据不可伪造。
