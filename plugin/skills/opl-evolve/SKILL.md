# 用进化式搜索改良一个算法实现

```bash
# 下文用 $OPL 指代插件的 bin 目录（agent 的 cwd 是用户工作区，不是插件目录）。
OPL="${KIMI_PLUGIN_ROOT:-<插件根>}/bin"
```

## 谁做什么：变异归你，可复核性归工具

`doc/plan/01-overview.typ` 定的分工是「变异算子留给宿主 agent，可执行文件只做
**数据库 + 评估器 + 沙箱**」。所以：

- **你**负责提变异：读任务书、改可进化区、交候选。
- **工具**负责保证你交出来的东西**可被独立复核、可去重、不会越界**。

工具**不**替你搜索，也不替你判断「哪个更好」——它只记录指标并给出去重与拒绝的理由。

## 四步，一步一条命令

## 评估器必须是**两阶段**的（硬约定）

```bash
python3 evaluator.py extract --problem P --candidate C --artifacts DIR   # 跑候选，只产出数据
python3 evaluator.py verify  --problem P --artifacts DIR --metrics-out M # 没有候选，独立判定
```

插件把这两步跑在**两个独立的沙箱进程**里：`extract` 那一侧有候选，`verify` 那一侧
**没有候选**，只读 `DIR` 里的数据并自己独立判定。

**为什么是硬约定而不是建议**——实测（审阅稿第二轮）：候选在可进化区里放

```python
import itertools
itertools.product = lambda *a, **k: [(0, 0, 0, 0)]
```

就把**评估器进程内**的枚举器换掉了。区外文本一字未改、冻结的题目参数也没变，于是
评估器只查一个全零输入就报 `sorts=true, comparators=0`，插件给它退出码 0。

**只读挂载挡不住这个**：它保护的是文件，而候选改的是**进程内存**。边界只能画在进程上。
不合规的评估器（只有一个 `--candidate` 入口的老写法）会被 `init` **直接拒绝**，
不会降级——降级选项一旦存在，早晚会被用来绕过。

### 1 建库：把骨架、评估器与实验定义钉住

```bash
$OPL/opl-evolve-init --lab lab --skeleton ./sortnet/skeleton.py \
  --evaluator ./sortnet/evaluator.py --problem ./sortnet/problem.json
```

`--problem` 是**冻结的实验定义**：题目参数 + 指标契约（什么算可行、优化哪个字段、
各字段什么类型）。它会被拷进实验目录，并以**只读**方式挂给评估器。三条理由：

- **区外文本不变，不代表题目不变。** 实测把 `N = 0` 放进区内重新绑定，就能让评估器
  看到一个零路问题并报 `sorts=true, comparators=0`——而区外一字未改。区外逐字节比对
  比的是文本，题目是**运行时行为**。所以题目参数由 `--problem` 给出，候选声明的值
  必须与它一致，不一致直接拒。
- **可行性不能由插件猜。** 插件原先硬编码 `sorts`，一个返回 `{"feasible": true,
  "loss": …}` 的通用评估器其候选会被判成「不可行」。
- **只读**：一个能改定义的候选等于自己出题自己判。

骨架与评估器会被**拷进** `lab/evolve/`。为什么是拷贝而不是记路径：区外比对的基准
必须稳定——指着一个会被编辑的外部文件，「区外没变」这个判断就失去意义。

`init` 会把骨架评估一遍并把指标记进第 0 代。**这很重要**：不评估的话基线没有指标，
「比骨架好」就没有可比对象，而且**你没法事后补**——同一份代码再提交会被 `code_hash`
判为重复（实测）。

`init` 加 `--force` 重建时不会原地复用旧实验：整个旧实验目录（骨架、评估器、实验定义、
运行史与库）会被挪到 `<lab>/.evolve-bak-<YYYYmmddTHHMMSS>`，路径打在 stdout 上。为什么
必须归档而不是留着：换了实验定义或评估器之后，旧成绩与新定义**不可比**，留在同一张表里
会让 `best` 排出一个不存在的「最好」——库里看起来有历史，其实那是另一个实验的历史。
为什么是**整个目录**而不是只把库文件挪走：库里的成绩是配旧骨架的，只恢复库等于留下一个
新旧混合的实验——成绩对不上骨架，而且两边都不是能复现的那个。

顺序是**先验完三份新输入，再在暂存目录把整个新实验建完，最后整体切换**。第一步：骨架、
评估器、实验定义三个源文件都得在，实验定义得合法，两阶段协议得探测通过。探测拿的是
**源文件**，此刻它们还没被拷进任何实验目录。三关都过了才碰活实验——反过来就是「报错退出，
但活实验已经不见了」，而一次骨架路径写错、或评估器不合协议的重建请求，不该改变现有实验
的状态。

第二步全在 sibling 暂存目录 `<lab>/.evolve-new-<时间戳>` 里做：拷三份文件、跑基线评估、
建库、写运行史。为什么不在活实验里就地做：复制阶段失败（新骨架拷成功、新评估器拷失败）
会留下新旧混合的实验——库被放回去了、骨架却已换新，而库里的成绩是配旧骨架的。暂存阶段
任何一步失败（复制、评估、数据库写入）都清掉暂存目录，**活实验一个字节都没动**，报错也
这么说。

第三步才整体切换：两次 `os.replace`，都在同一个文件系统内。归档名按「不存在就取下一个」
定：`<lab>/.evolve-bak-<时间戳>` 被占就退到 `-2`、`-3`…。不这么做的话，同一秒里重建两次会
撞名，而归档用的 `os.replace` 是**覆盖式**的——第二次会静默吃掉第一次的备份，而两份备份
之间恰好是「另一个实验」，吃掉哪一份都等于丢历史。

切换本身失败（盘满、权限）时旧实验会被放回原处：宁可退回「重建没发生」，也不留一个换到
一半的实验目录。切换成功之后还要把运行史里记的**暂存期路径**改写成正式路径——否则
「这个数字哪来的」指向一个已经不存在的目录。

### 2 要一份变异任务书

```bash
$OPL/opl-evolve-suggest --lab lab --metric comparators --where sorts=true
```

它给你：可进化区原文、不可动的区外、若干**带理由**的亲本、以及提交时会被执行的约束。
亲本清单里每一条都写了为什么挑它（最好者 / 某代的其他代表 / 次优）——没有理由的
亲本清单是不可复核的。

### 3 提交候选

候选必须是**完整文件**（含区外原文），不是片段：

```bash
$OPL/opl-evolve-eval --lab lab --candidate ./cand-01.py \
  --generation 1 --operation mutate
```

### 4 看库

```bash
$OPL/opl-evolve-show --lab lab --best comparators --where sorts=true
```

## 三条纪律，每条都有对应的退出码

| 纪律 | 违反时 | 为什么 |
|---|---|---|
| 区外**逐字节**不许变 | `2` | 「研究者写死骨架」得由工具执行，不能靠自觉。改一个空格也算改动——这条刻意取严，因为它会误拒「只重排格式」，却绝不会放过一次真实的区外改动，而两种错的代价不对称 |
| 同一份程序不许占两个库位 | `5` | `code_hash` 取归一化 token 序列的 sha256（吸收注释、行尾、CRLF、缩进风格；**不**吸收语义改动）。去重由数据库的 UNIQUE 索引执行，不由调用方自觉 |
| 题目参数不许由候选改 | `2`/`3` | 题目参数来自冻结定义，候选声明的值必须与之一致。实测：区外一字不改，只在区内重新绑定 `N`，就能把「四路排序」变成「零路问题」并报通过 |
| 不改可进化区就不是进化 | `1` | 退出码 `1` 表示「入库了，但评估不通过」。这不是拒绝，是**记录**：库要留住失败者，否则搜索会反复撞同一堵墙。它单独一条的用途是让你别再往那边走 |

## `best` 必须带可行性条件——否则你会得到一条假改进曲线

这是最容易踩、后果最坏的一处。实测：库里有一条 4 个比较器的候选，它
**并不排序**（`sorts=False`）。不加过滤时：

```
$OPL/opl-evolve-show --lab lab --best comparators
→ id=3 sorts=False comparators=4     ← 数字最小，但它是个坏程序
```

「从 6 个改进到 4 个」听起来像一次提升，实际上是把不可行的东西当成了成绩。
**可行性必须显式给出**：`--where sorts=true`。工具刻意不替你猜哪个字段意味着
「可行」——猜错的那一次就会静默产出一条假曲线。

同理，`metrics` 里**没有**该指标的行不参与比较（不会被当成 0）。把「没测出这个指标」
当成最小值，正好会在「改进」这件事上造出假结论。

还有一类不可比**不来自数字，而来自实验**：换了实验定义或评估器之后，同名字段量的不是
同一件事。所以 `--best` 只考虑「最近一次评估用的实验定义 sha256 + 评估器 sha256」都与
当前实验一致的成绩，不一致的跳过——跳过时打印「跳过了 N 条**不同实验定义/评估器**的成绩
——同名指标不代表可直接比较」。这句提示不能省：没有它，「跳过」和「库里本来就没有」
看起来一模一样，而两者的下一步完全不同。

## 评估器用退出码表态：`0` / `1` / `2` / `≥3`

评估器的 `exit` 是它给结论的第二个出口，四个区间各有各的意思：

| 评估器退出码 | 意思 | 插件怎么用 |
|---|---|---|
| `0` | 跑完了，指标有效 | 采信指标。**可行不可行由实验定义的 `feasible` 字段给出**，不由退出码决定 |
| `1` | 按约定不可行 | 这是**结论**不是故障——照实入库，搜索要留住失败者 |
| `2` | 拒收这个候选 | 候选不合格（例如它声明的题目参数与冻结定义不一致），去修候选 |
| `≥3` | 评估器自身故障 | 它写的**任何**指标都不采信：故障时产出的数字本身就没有意义 |

**为什么退出码不等于判决**：`0` 只说「指标写出来了」。可行性来自实验定义，把两者
混为一谈，一个通用评估器（返回 `{"feasible": true, …}`）的候选就会被退出码判成不可行。

**退出码与指标矛盾时不下判决**（`verdict_conflict`）：退出码 `1` 而指标说可行，或退出码
`0` 而指标说不可行，都返回 `UNKNOWN`（退出码 `3`），并把退出码与 `feasible` 字段这两份
原始信息一起留在理由里。两份信息互相打脸，说明**评估器自己不自洽**；此时任选一份当
成功依据都是自欺——工具能做的只有拒绝下结论。

这条判决**只有一处实现**，`init` 与 `eval` 共用：初始化评估骨架与提交候选走的是同一段
代码。不共用的话，同一次结局会在一处被记成成绩、在另一处被拒收，而两边的分歧不会报错，
只会让库里的基线悄悄不可信。

## 判决与动作

（下表里出现的 `sorts` / `comparators` 是本仓库排序网络夹具的字段；换成你的问题时，
字段名与「什么算可行」都来自你的实验定义——插件不认识具体字段名。）

| 判决 | 退出码 | 动作 |
|---|---|---|
| `EVALUATED` | 0 | 入库且评估通过。可以继续从它出发变异 |
| `INFEASIBLE` | 1 | 入库但按定义不可行。这只否定**这一个候选**——它不否定它的邻域，也不否定这条构造路线。下一步该改什么，取决于你看到的失败长什么样 |
| `INVALID` | 2 | 候选不合格（缺标记 / 区外被改），或**评估器产出的指标不符合实验定义**。前者去修候选，后者去修评估器 |
| `NO_VERDICT` | 3 | 没有判决可取：沙箱没给出结局（超时 / 被 OOM 杀 / 被杀），评估器自己崩了（退出码 `≥3`，它写的指标不采信），或者它的退出码与指标互相矛盾（`verdict_conflict`——评估器不自洽）。**这不是「候选不行」**——可能是预算不够、候选跑飞，或者评估器前后不一 |
| `SANDBOX_MISSING` | 4 | 找不到 bwrap。工具不降级到裸跑，因为那会静默丢掉整个隔离保证 |
| `DUPLICATE` | 5 | `code_hash` 命中，没有新增。换个变异 |

`3` 与 `1` 的区别是本技能最要紧的一处：**「没跑出来」不是「跑出来是错的」**。
把前者报成后者，会让你去修一个本来没问题的候选。矛盾（`verdict_conflict`）也落在 `3`：
评估器跑完了，但它的话前后不一——那同样不是「候选不行」。

## 评估器是你写的——它对不对，工具管不着

工具只保证「评估器在沙箱里跑、结果落盘、指标可追」。评估器本身的正确性你得自己
负责，两条最低要求：

- **确定性**：同一份候选两次评估必须给同一组指标。做不到的话「改进」全是噪声。
- **给依据，不只给布尔**：`sorts: false` 单说一句是没法复核的，要能说出查了多少个
  输入、第一个反例是什么。
- **类型要对**：`sorts` 必须是真布尔，不能是字符串 `"false"`——后者在 Python 里是
  真值，会被判成通过。插件的实验定义会替你拦下这类错，但评估器本来就不该产出它。仓库里的排序网络评估器（`tests/fixtures/sortnet/evaluator.py`）
  是一个可照抄的样本——它按 0-1 原理枚举 `2^n` 个输入，并对每个判定给出计数与反例。

## 反面用法（不要这样用）

- **不要用截断/抽样冒充判定。** 排序网络这一例之所以成立，是因为 0-1 原理让它成为
  **判定**而非抽样；换成抽样，你会得到一个永远通过的假验收。
- **不要把不可行的候选当成「接近成功」。** 数字小不是成绩：本仓库夹具是排序网络，
  4 个**能排序**的比较器才是成绩，4 个不能排序的只是个更短的坏程序。换成你的问题时，
  「什么叫可行」由你的实验定义给出，不由数字大小推断。
- **不要因为一次不可行就放弃一条路线。** 一次失败否定的是**这一个候选**；
  它不否定它的邻域，也不否定这条构造思路。下一轮改什么，取决于失败长什么样。
- **不要在区外「顺手」改注释或格式。** 会被拒，而且那意味着你在改骨架——骨架是
  研究者钉住的，改它得先改骨架本身并重建库。
